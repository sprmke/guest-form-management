## 1. What it is

A chat assistant embedded in the admin dashboard (floating launcher, bottom-right, hidden for super-admins) that answers operational questions and executes actions — strictly scoped to the signed-in user's real RBAC permissions, never more. Two-layer kill switch (platform-wide off by default, org opt-in, optional per-property disable). **Plan gating:** property must have **`aiDashboardAssistant`** on its subscription (`useAiAssistantAccess` + `dashboard-assistant-chat` check before quota). Gemini 2.5 Flash via `_shared/geminiToolCallClient.ts`, tool-calling loop capped at `MAX_TOOL_ROUNDS = 4` rounds per turn.

## 2. Safety model (applies to every tool, no exceptions)

1. **Independent RBAC re-check.** Every tool re-derives the permission it needs and re-runs the real RBAC primitive (`verifyPropertyAccess` / `verifyOrgAccess` / `verifyOrgOwner` / `verifyPropertyOwner` / `verifyOrgTeamAccess` / `requireTeamPropertyAccess`) against the **original request's JWT** — never anything the model asserts. A tool call with a forged/wrong `propertyId` in its arguments fails the RBAC check the same way a direct API call would.
2. **Three-tier risk model**, computed server-side, never by the model:
   - **Tier 0 (read)** — always allowed if the RBAC check passes. Never touches the database.
   - **Tier 1 (auto-executed)** — runs immediately, surfaced to the host as a visible "done automatically" card. Reserved for idempotent or clearly-reversible writes.
   - **Tier 2 (confirm-required)** — the tool call returns a `proposed` result; nothing is written yet. A separate `dashboard-assistant-confirm` call (triggered by the host clicking Confirm in the chat UI) is the only path that actually executes it. A pending proposal expires after 15 minutes.
3. **Escalation rules that override a tool's normal tier** (`classifyActionRisk` in `dashboardAssistantRiskClassifier.ts`):
   - **Bulk escalation**: if the model requests 2+ write tools in one turn, every one of them is forced to Tier 2, regardless of what each would individually resolve to.
   - **Cross-scope escalation**: if a tool's target booking/property differs from what `pageContext` says the host is currently looking at, it's forced to Tier 2.
   - `propose_transition_booking` specifically has **no fixed tier** — it's computed per-call from the real booking-status graph (`statusMachine.ts#canTransition`): a plain forward, non-financial, non-override edge is Tier 1; anything that's a manual-override edge, a cancellation, an SD-refund finalization, or carries a financial payload field is Tier 2.
4. **Immediately-before-execution re-check** (`assertActionSafeToExecute`). Even a Tier 1 tool re-derives its tier from current DB state right before writing — a booking's status may have changed between proposal and execution; the guard hard-throws if the recomputed tier disagrees with what was expected. This runs for Tier 0/1 auto-execution and for Tier 2 confirm-execution alike.
5. **Post-generation grounding check** (`assertBlocksGrounded` in `dashboardAssistantSafetyGuard.ts`) — every response block is checked against the actual tool-result data before being sent to the host; ungrounded blocks are dropped, not shown. Empty `stat_list` / `data_table` / `link_list` / `file_list` cards are stripped (`sanitizeAssistantChatBlocks`); if the model still omitted `pendingTasks`, `bookedStays`, or a requested booking file that a tool actually returned, `hydrateAssistantBlocksFromTools` fills them in. Status codes in text (`READY_FOR_CHECKOUT`) are rewritten to human labels. `file_list` URLs must match a tool-returned storage URL (never a model-invented link); the UI signs private buckets at preview time via `get-booking-asset-url`.
6. **Full audit trail** — every executed write (Tier 1 auto or Tier 2 confirmed) is recorded and surfaced on the relevant booking/property's "Actions taken by AI assistant" card.
7. **External-facing actions are a stricter, separate risk category** (scaffolded in Phase 2, now used by `propose_send_inbox_reply` and `propose_publish_to_meta` — see §3.7). Sending a real message to a guest or publishing to a public social account is categorically riskier than any internal DB write, always Tier 2, with its own distinct destructive-styled confirm UI.
8. **A "never build" list exists at the tool-catalog level, not just as a prompt instruction** — irreversible/maximal-blast-radius actions are simply never registered as callable tools (see §6). No amount of prompting can make the model call a tool that doesn't exist.

**`propose_update_org_profile` and `propose_update_property_profile` were reclassified Tier 1 → Tier 2 on 2026-08-17**, after a review pass caught that `propose_update_org_profile`'s patch fields include `contactName`/`contactRole`/`contactPhone`/`contactEmail` (confirmed directly against `OrgProfilePatchInput` in `orgProfileService.ts`) — those feed guest-facing communication, so a silently auto-executed change (e.g. from a manipulated/prompt-injected turn) could redirect guest inquiries to an attacker's contact info with zero host review. `propose_update_property_profile` doesn't actually carry contact fields (`PropertyProfilePatchInput` is just `name`/`address`/`maxGuests`/`status`/`tower`/`unitNumber`/`residenceName` — verified directly, not assumed) — it was moved to Tier 2 alongside it on the more conservative but still real basis that `status` (ACTIVE/INACTIVE) has genuine operational impact (hides the listing, blocks new bookings), and the cost of requiring one confirm click here is low. `propose_update_property_settings` was already Tier 2 from Phase 4 for a third, independent reason (cancellation policy/house rules/amenities are guest-facing terms) — all three tools land on Tier 2 now, each for its own documented reason, not by copy-pasting one rationale across all of them.

**Not built / deliberately excluded from `propose_update_property_settings`**: payment methods, GAF/pet document requirements, email automation toggles, media. `properties.settings` holds these too, but none of them has a dedicated server-side validator anywhere in this codebase (only the fields in the table above do, via `validatePropertySettingsPatch`) — there's nothing safe to validate a chat-driven write against yet. Building the tool without a real validator would mean trusting the model's own judgment on a JSONB blob with no safety net, which is exactly what this whole tier system exists to avoid. **Add the validator first, then the tool.** `propose_update_property_templates_settings` (GAF/pet PDF template content) was skipped entirely, not deferred — template content is long-form legal/compliance document text; a chat tool that can silently rewrite it is a bad fit at any risk tier, confirm dialog or not.

### 3.4 Parking (Phase 5)

Statuses: `PENDING_HOST_ACCEPTANCE → PENDING_REVIEW | NO_HOST_AVAILABLE | CANCELLED`, `PENDING_REVIEW → READY_FOR_CHECKIN | CANCELLED`, `READY_FOR_CHECKIN → COMPLETED | CANCELLED`.

| `propose_claim_parking_booking`      | write | **2 (always)** | `bookings:edit` (parking-scoped)                       | Atomically accept a broadcast request — first-Accept-wins, commits the slot, emails the guest a confirmation                                             |
| `propose_decline_parking_booking`    | write | **2 (always)** | `bookings:edit` (parking-scoped)                       | Decline this slot's candidacy; if every candidate has declined, the request terminates to `NO_HOST_AVAILABLE` and the guest is notified once             |
| `propose_transition_parking_booking` | write | **2 (always)** | `bookings:edit` (parking-scoped)                       | Post-broadcast status change only — rejects any attempt to transition out of `PENDING_HOST_ACCEPTANCE` directly, mirroring the real endpoint's own guard |

**All three write tools are unconditionally Tier 2**, not just by default classification but registered directly in `TIER2_ONLY_TOOL_NAMES` — even a routine post-broadcast transition sends a guest-facing notification, and the claim/decline race guard (`.eq('status', 'PENDING_HOST_ACCEPTANCE')`, guarded atomic UPDATE) is safety-critical. The claim/decline logic itself was extracted from `claim-parking-booking`/`decline-parking-booking` into a new shared `_shared/parkingBroadcastActions.ts` (both edge functions now call it too) specifically so this race-safe guard has exactly one implementation — a second, chat-tool-only copy of "first Accept wins" logic would be a real correctness risk if the two ever drifted.

**Not built / explicitly excluded**: re-triggering `submit-parking-booking-request` or any broadcast fan-out — mass-notifying spot owners is a distinct, higher-blast-radius action category from a single claim/decline and needs its own design pass, not a tool wrapper. Parking slot payment settings (`parking-settings` — GCash number, payment methods) were left out of the read/write catalog for the same reason as property payment methods (§3.3): no dedicated validator exists to check a write against, and reading account numbers via chat carries its own exposure even read-only.

### 3.5 Pricing (Phase 6) — property + parking

Covers both `_shared/propertyPricing.ts` and `_shared/parkingPricing.ts`. **Critical implementation detail discovered while building this phase**: `savePropertyPricing`/`saveParkingPricing`'s `dateOverrides` and `holidayRules` patch fields are a **full replace of the stored map/array, not a merge** — passing `{dateOverrides: {"2026-12-31": 8000}}` would silently **delete every other date override the host has ever configured**, not just add one. Every override/holiday-rule tool below reads the current value first and writes back the merged result — never just the one new entry.

**Not built / explicitly excluded**: any tool accepting more than one date/rule per call. `dateOverrides`/`holidayRules`/`unblockDateKeys` could technically carry many entries in one request, but every tool here is deliberately single-target (one date, one rule, one range ≤62 days) — a bulk rate change (e.g. "raise all December weekends 20%") stays unbuilt; it needs an explicit diff/preview step shown to the host before any multi-date write, which is separate design work, not a natural extension of this phase's tools.

**`propose_send_inbox_reply` is the assistant's first `EXTERNAL_SEND_TOOL_NAMES` member** (see §3.7 for what that means). The real `social-inbox-send` edge function was **not** refactored to share it: that endpoint's feature set is intentionally broader (attachments, private replies, reply-to-message threading) than what a chat tool should attempt to fill from free text, so the two implementations diverge on purpose rather than being forced into one abstraction that fits neither well. Confirming this action in the chat UI shows visibly different copy and a destructive-styled "Send" button instead of the generic "Confirm" — see §3.7.

**Not built / explicitly excluded**: any tool that can flip `auto_reply_mode` to `'send'` — `get_inbox_settings` is read-only, full stop, no corresponding `propose_update_inbox_settings` tool exists. That toggle changes standing system behavior (the platform auto-sending AI replies going forward, no human in the loop per message) — a fundamentally different and higher-stakes action than one assistant-drafted, host-confirmed reply, and was explicitly named in the original v2 plan as needing its own design review before ever being chat-exposable. Message attachments, private replies, and reply-to-message threading are also out of `propose_send_inbox_reply`'s scope for the same reason `propose_update_property_settings` stays narrow — start with the well-understood, safely-validated slice.

### 3.7 External-facing actions — the stricter risk category, now in real use (Phase 2 scaffold → populated)

`_shared/dashboardAssistantRiskClassifier.ts` exports `EXTERNAL_SEND_TOOL_NAMES` — now containing `propose_send_inbox_reply` (Phase 7) and `propose_publish_to_meta` (Phase 8). `isExternalSendTool()` gates two things end-to-end:

1. **Classification**: any tool in this set is always Tier 2, registered directly in `TIER2_ONLY_TOOL_NAMES` too — never left to fall through the generic default-tier logic.
2. **Confirm UI**: `dashboard-assistant-chat/index.ts` sets `isExternalSend: true` on the `action_confirmation` block for these tools; `ActionConfirmationBlock.tsx` renders a destructive-tinted card, an explicit "sends/publishes for real, right now — can't be undone" warning line, and a "Send" button (destructive variant) instead of the generic "Confirm" — visually and textually distinct from every other Tier-2 confirmation in the app, so a host can't mistake it for an internal-only, easily-undone action.

### 3.8 Marketing Studio (Phase 8) — different RBAC tier, by necessity

**Marketing Studio has no property-team RBAC today.** Every marketing edge function (`marketing-templates`, `generate-marketing-caption`, `generate-marketing-template`, `marketing-music`, `publish-to-meta`) gates on `serveAdmin`/`verifyAdminJwt` — the global `ADMIN_ALLOWED_EMAILS` allowlist — not `verifyPropertyAccess`/`TeamPermissionId` like every other module in this catalog. This is a real, pre-existing characteristic of the app (confirmed by reading each endpoint directly), not something introduced here. Building real per-property `marketing:view`/`marketing:edit` permissions was scoped as a real option and explicitly declined for this pass (2026-08-16) — it would mean touching the permission catalog, built-in role definitions, the custom-role UI, and migrating 6 edge functions, a standalone feature in its own right. **These tools instead mirror today's real boundary exactly, which is actually two checks, not one**: `verifyMarketingAdminAccess()` calls `verifyAdminJwt(ctx.req)` (global allowlist) and _then_ `resolveAdminPropertyId(ctx.req, admin.id, propertyId)` for the specific target property — and that second call internally runs `verifyPropertyOwner`, which requires the caller to also be that property's org owner (or a platform admin). So the real, combined gate is **global admin allowlist AND (org owner OR platform admin)** — exactly what the real marketing edge functions already enforce via the same two-step (`serveAdmin` then `resolveAdminPropertyId` inside the handler), not `verifyAdminJwt` alone. A host who fails either check gets a plain access-denied refusal — same as calling the real endpoints, and same as the real Marketing Studio UI today. This is the accurate, current state of the product, not a gap this session introduced.

| Tool                            | Type  | Tier                           | RBAC                          | What it does                                                                                                                                                                        |
| ------------------------------- | ----- | ------------------------------ | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list_marketing_templates`      | read  | 0                              | global admin + property owner | Saved calendar/design/video templates for a property                                                                                                                                |
| `get_marketing_publish_history` | read  | 0                              | global admin + property owner | Recent Meta publish history (up to 10)                                                                                                                                              |
| `search_marketing_music`        | read  | 0                              | global admin + property owner | Jamendo royalty-free track search — **read-only**, no import (see exclusion below)                                                                                                  |
| `draft_marketing_caption`       | read  | 0                              | global admin + property owner | AI-drafted social caption — pure generation, never posted. Classified Tier 0 despite requiring admin access, same reasoning as `draft_inbox_reply`                                  |
| `draft_marketing_template`      | read  | 0                              | global admin + property owner | AI-drafted design tokens for the visual editor — pure generation, never saved                                                                                                       |
| `propose_publish_to_meta`       | write | **2 (always) + external_send** | global admin + property owner | **The single highest-blast-radius tool in this entire catalog** — publishes an image to a real, public Facebook Page or Instagram account (post/story/reel + caption), irreversibly |

**`propose_publish_to_meta`'s risk profile, explicitly**: the underlying media-URL resolver (`resolvePublicMarketingMediaUrl`) accepts **any** `https://` URL unchanged — that's an existing product decision in `marketingMediaUpload.ts`, not something tightened or loosened here. The only safety mechanism is the mandatory Tier-2 + external_send host confirmation, which shows the exact caption, media URL, and destination platform before anything fires — the same "human reviews the literal payload before clicking a destructive-styled button" pattern as `propose_send_inbox_reply`, just for a public post instead of a private message. Its core logic (media resolution, connection lookup, Graph API calls, publication-row lifecycle) was extracted into a new shared `_shared/marketingPublishAction.ts`, used only by this tool — the real `publish-to-meta` endpoint keeps its own richer implementation (Instagram scheduling, `scheduledAt` deferral) since that's out of scope for a first-cut chat tool.

**Not built / explicitly excluded**: importing/uploading music into the org's media library (`marketing-music`'s `import-jamendo`/`import-url`/file-upload actions) — importing from an arbitrary caller-supplied URL is exactly the kind of action that's riskier via a chat tool than a human clicking through a UI (a prompt-injected instruction embedded in guest-message content could plausibly steer a naive tool call toward fetching from an attacker's URL); only the read-only search stays exposed. Saving or deleting templates via chat — the generated design tokens are meant for a visual canvas editor, not a natural chat-managed object; `draft_marketing_template` already gives real value (draft content) without wading into library management. Any `marketing:*` RBAC permission — deliberately deferred, see above.

## 4. Architecture-level facts every tool call relies on

- **Grounding prompt** (`dashboardAssistantContext.ts#hostSafeGroundingFactsToPrompt`) injects, every turn: today's date + Asia/Manila timezone, the requesting host's name, org name/slug, the accessible property list, a 4-status booking-count summary, the resolved `permissions[]` array, and finance/maintenance month-to-date totals (only if the host has `finance:view`/`maintenance:view` and the org has ≤5 properties).
- **Tool-call loop**: up to 4 rounds; Gemini can request multiple tool calls in one round, and results feed back for further reasoning. On round exhaustion, the assistant still attempts to synthesize a real answer from whatever was gathered (not just a canned "ask again" message) via a final structured-output call over the accumulated tool-call history.
- **Knowledge base**: `search_knowledge_base` reads `ai_dashboard_assistant_knowledge_base`, populated by `bun run sync:ai-knowledge-base` (local) / `:dev` (hosted dev) from the "Host-facing knowledge" Q&A sections in `docs/guides/routes/**/*.md`. **This has no automatic trigger** — re-run it by hand whenever a route guide's knowledge section changes, or the tool silently returns stale/empty results.
- **Attachments**: hosts can attach images/PDFs to a chat turn (paperclip in composer); stored via `_shared/dashboardAssistantAttachments.ts`, passed to Gemini as multimodal parts. Primarily used for payment-receipt review (pairs naturally with `run_receipt_validation`).
- **Booking files in replies**: `get_booking` / `get_booking_documents` return the same Files-tab storage URLs (approved GAF, pet forms, receipts, IDs, parking). Chat renders them as `file_list` cards; invented URLs are dropped. Private buckets (`approved-gafs`, `approved-pet-forms`, `sd-refund-receipts`) are signed in the UI via `get-booking-asset-url`, same as booking detail.
- **Conversation history**: `dashboard-assistant-conversations` (GET, list + single) backs the panel's History view; conversations are private per user, capped at the 20 most recent (no pagination yet).

## 5. Explicitly excluded — never build without a dedicated design review

These are intentionally **not** tool-catalog entries, enforced by simply never registering them — not by prompt instruction, which the model could in principle be talked around:

| Action                                                                                                                              | Why excluded                                                                                                                                                                                                                                                                                  |
| ----------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `delete-organization`                                                                                                               | Owner-only, irreversible, cascades property/storage cleanup. Should probably never be assistant-reachable at all, even at Tier 2 — the blast radius (an entire organization and everything under it) is categorically different from anything else in this catalog.                           |
| `delete-property`                                                                                                                   | Same reasoning as org deletion — irreversible, cascading, blocked only by existing bookings today.                                                                                                                                                                                            |
| Org-ownership transfer                                                                                                              | Doesn't exist as a feature yet; if built, treat as irreversible-equivalent to deletion.                                                                                                                                                                                                       |
| Payment provider credential changes                                                                                                 | Financial-config change with its own existing in-app confirm dialog; don't fold into the generic Tier 2 flow — this needs its own review, not a reuse of the pattern built for booking transitions.                                                                                           |
| `approve-org-verification` / `reject-org-verification`                                                                              | Super-admin only, outside org/property RBAC entirely — categorically out of scope for a host-facing assistant by definition, not a scoping choice.                                                                                                                                            |
| Bulk/range pricing writes (Phase 6 — verified excluded, not just planned)                                                           | Every pricing write tool is deliberately single-target (one date, one rule, one ≤62-day range). | Re-triggering parking broadcast fan-out (Phase 5 — verified excluded, not just planned)                                             | Mass-notifying spot owners is a distinct, higher-blast-radius action category from a single claim/decline — needs its own design pass.                                                                                                                                                        |

| Flipping inbox `auto_reply_mode` to `'send'` (Phase 7 — verified excluded: `get_inbox_settings` is read-only, no write tool exists) | Changes standing system behavior (the platform auto-sending on the host's behalf going forward) — a fundamentally different and higher-stakes action than a one-off assistant-drafted reply.                                                                                                  |
| Inbox message attachments, private replies, reply-to-message threading (Phase 7)                                                    | `propose_send_inbox_reply` is deliberately narrower than the real `social-inbox-send` endpoint — text + conversationId only, same reasoning as every other narrowed-scope tool in this catalog.                                                                                               |
| `propose_update_property_templates_settings`                                                                                        | See §3.3 — long-form legal/compliance document content, bad fit for chat editing regardless of tier.                                                                                                                                                                                          |
| Property `settings` sub-fields with no validator (payment methods, doc requirements, email automation, media)                       | See §3.3 — no safety net exists to validate a chat-driven write against.                                                                                                                                                                                                                      |
| Marketing music import/upload (Phase 8 — verified excluded, only search is exposed)                                                 | Importing from a caller-supplied URL is riskier via a chat tool (prompt-injection-steerable) than a human clicking through a UI; only Jamendo's own read-only search stays exposed.                                                                                                           |
| Marketing template save/delete via chat (Phase 8)                                                                                   | Generated design tokens are meant for a visual canvas editor, not a chat-managed object; `draft_marketing_template` already delivers value without library management.                                                                                                                        |
| `marketing:*` property-team RBAC (Phase 8 — explicitly declined 2026-08-16, not forgotten)                                          | Real per-property marketing permissions would require touching the permission catalog, built-in roles, the custom-role UI, and migrating 6 edge functions — a standalone feature. Marketing tools instead mirror today's real global-admin-only boundary (`verifyAdminJwt`). See §3.8.        |

## 6. Out of scope — nothing meaningful to expose (verified, not assumed)

- **Notifications module** — read/consume-only for hosts; no host-side notification-rule CRUD exists to wrap.
- **Voucher system** — guest/system-facing only; the admin dashboard only displays results read-only.
- **Guest portal** — separate guest-authenticated identity with zero host-facing management surface.
